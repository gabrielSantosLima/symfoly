# Commit and push

Use this skill only when the user asks to commit, commit and push, or ship the
current changes.

## 1. Read the project policy

Read `AGENTS.md` and `.harness.json` when present. They define:

- the check commands;
- the commit autonomy: `commit-and-push-when-asked`,
  `commit-only-when-asked` or `strict`;
- the local-only files that must never be staged.

With `strict`, confirm each git write action separately. With
`commit-only-when-asked`, never push unless the user asks for it in a separate
instruction.

## 2. Inspect the repository

```bash
git status --short
git branch --show-current
git diff
git diff --cached
git log --oneline -5
```

Read the full diff before staging anything. Use the recent log to match the
repository's commit style. If the user named specific files, stage only those.
If the working tree contains unrelated changes, do not include them; ask which
changes belong to the commit.

## 3. Run the checks

Run every command declared in `AGENTS.md` or `.harness.json`. A failing check
blocks the commit: fix the problem first. Do not skip hooks with `--no-verify`
unless the user explicitly asks.

## 4. Stage explicit paths

```bash
git add path/to/file path/to/other
```

- Never use `git add -A`, `git add .` or `git commit -a` unless every reviewed
  change belongs to the same commit.
- Never stage local planning files, secrets, environment files, build output or
  generated artifacts.
- Review the staged diff with `git diff --cached`.

## 5. Write the message

Follow Conventional Commits, in English, short and imperative:

```text
<type>(<optional scope>): <short description>
```

Allowed types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `perf`,
`build`, `ci`, `style`.

- Keep the subject under 72 characters, lowercase, without a trailing period.
- Use the body only when the change needs context (why, trade-offs,
  references); wrap it at 72 columns.
- Never add AI authorship or co-author trailers: no `Co-Authored-By`, no
  "Generated by ...", no tool, agent or session attribution.
- Never mention the agent, the prompt or the session.
- Split unrelated work into separate commits when the user asks for a clean
  history.

## 6. Commit

```bash
git commit -m "type: short description"
```

If a hook fails, read the output, fix the cause and commit again. Do not amend,
rebase or squash existing commits unless the user explicitly asks.

## 7. Push

Only when the project policy and the user allow it:

```bash
git push
```

If the branch has no upstream, use `git push -u origin <branch>`. Never
force-push unless the user explicitly requests it on a branch they own. If the
push is rejected as non-fast-forward, stop and report instead of rewriting
history.

## 8. Verify and report

```bash
git status --short
git log -1 --oneline
```

Report the branch, the commit hash and subject, and confirm whether the working
tree is clean. Say what was intentionally left uncommitted and why.

## Boundaries

- This skill never creates tags or releases. Releases use `release-cut`.
- Never commit generated artifacts that the repository ignores.
- Never commit or push when the user only asked to review changes.
